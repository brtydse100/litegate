# LiteGate 2.0.0

LiteGate 2.0 turns the self-hosted LiteLLM key portal into a complete access and automation layer. It adds persistent local users, flexible OIDC administrator mapping, a stable management API, and administrator-only bulk key policy editing while keeping the everyday dashboard lightweight.

## Highlights

- **Fast dashboard:** Normal page loads use the compact spend and policy data already present in LiteLLM key records. They do not fetch raw spend logs. Installation-wide key data is requested only when an administrator opens the paginated bulk editor.
- **Local users:** Administrators can create local accounts, assign `user` or `admin` roles, reset passwords, and disable or re-enable access. Local account state is stored in SQLite and can be persisted by Docker Compose or Helm.
- **OIDC administrator mapping:** Any standards-compliant OIDC provider can be used. Administrators may be matched case-insensitively by configured email addresses or group values, including nested claims such as `realm_access.roles`.
- **API v1:** `/api/v1` supports identity inspection, scoped or administrator key listing, key creation, bulk policy updates, and local-user management. Trusted automation can use the optional installation-wide management API key instead of a human password.
- **Administrator-only bulk editing:** Only administrator portal sessions and the management API credential can bulk-edit keys. LiteLLM-key identities and normal users are rejected by the API, and the editor is shown only to administrators.
- **Clearer interface:** Key secrets have one-time reveal and copy behavior, regeneration requires confirmation, and the Users and bulk-editor views explain permissions and actions more directly.
- **Operations and security:** The release includes Docker Compose and Helm deployment paths, persistent account storage, a health endpoint, signed OIDC state, verified ID tokens, password hashing, session-state rechecks, key-operation rate limiting, bounded bulk-update concurrency, and Nginx browser security headers.
- **Documentation:** The repository includes a product banner and reorganized setup, API, configuration, security, and deployment guidance.

## Upgrade and configuration notes

1. Preserve or back up the local-user data volume before replacing an existing container. New installations create the SQLite database automatically at `local_users_db_path`.
2. Rebuild the image, or pull the published 2.0.0 container package when it is present after a successful package workflow run. Do not assume the package exists until the workflow has completed.
3. Replace sample values for `litellm_master_key` and `jwt_secret`. Configure `root_url`, CORS origins, and HTTPS for the public deployment.
4. To enable OIDC, set the issuer, client ID, client secret, callback URI, and scopes. Add `admin_emails`, or configure `admin_groups` with the correct `oidc_groups_claim`; the selected claim must be present in the ID token.
5. To use managed local accounts, keep `local_users_enabled` enabled and mount persistent storage for `local_users_db_path`. Treat the bootstrap local administrator as a setup or recovery credential and change its sample password before use.
6. To enable automation, set a long random `management_api_key`, store it as an administrator secret, and send it with `X-API-Key`. Version 2.0 provides one installation-wide management credential rather than per-agent scopes.
7. Review new-key defaults for model access, budget, reset duration, TPM/RPM limits, key duration, and team assignment before issuing keys.

There is no manual schema migration step for local accounts in this release. LiteGate initializes the local-user table when the backend starts; retaining the configured database path or persistent volume retains those accounts.

## Validation

The release worktree was validated on 2026-08-20 with:

- 22 passing backend tests covering API authorization, authentication, configuration, LiteLLM integration behavior, local users, and rate limiting;
- a successful TypeScript and Vite production build; and
- `npm audit --omit=dev` reporting zero vulnerabilities.

Container publication is performed separately by the package workflow and is not asserted by these application checks.

## Compatibility and limits

- LiteGate requires a reachable LiteLLM management API and its master key.
- Bulk requests accept up to 100 keys and return an individual result for each key.
- The management API key grants installation-wide administrator access; rotate it if exposed.
- A LiteLLM virtual key can identify and inspect only itself and cannot bulk-edit keys.
