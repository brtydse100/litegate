# LiteGate 2.4.0

LiteGate 2.4 closes a key-regeneration budget bypass and hardens the packaged
runtime so it no longer needs root privileges.

## Highlights

- Regenerated credentials inherit the accumulated spend of the keys they
  replace, so rotating a secret does not refresh its configured per-key budget.
- Key, local-account, team, and bulk-edit buttons are disabled during the
  server-enforced cooldown and display the remaining wait time.
- The Docker image runs as UID/GID `10001:10001`; Nginx uses unprivileged port
  `8080`, while Compose and Helm still expose port `80` to clients.
- The Helm chart enables `runAsNonRoot`, drops every Linux capability, prevents
  privilege escalation, applies `RuntimeDefault` seccomp, and uses `fsGroup`
  for persistent storage.

## Upgrade notes

Pull `ghcr.io/brtydse100/litegate:2.4.0` after the release workflow publishes
it. New Docker volumes work without preparation. If an existing named volume
was initialized by LiteGate 2.3 or earlier, migrate ownership once before
starting 2.4:

```bash
docker compose -f docker-compose.image.yml run --rm --user 0 \
  --entrypoint chown litegate -R 10001:10001 /app/backend/data
docker compose -f docker-compose.image.yml up -d
```

Kubernetes persistent volumes are prepared through the chart's `fsGroup: 10001`
setting. Clusters with a restricted policy can override the security contexts in
values, but the shipped defaults are the supported configuration.

## Budget behavior

LiteLLM records spend independently for keys, users, and teams. LiteGate now
preserves key-level spend across self-service regeneration. Continue setting
LiteLLM user or team budgets when you need a cumulative ceiling shared across
credentials created outside LiteGate.
