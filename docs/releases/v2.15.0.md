## What's Changed

> [!WARNING]
> Upgrade to [v2.15.1](https://github.com/brtydse100/litegate/releases/tag/v2.15.1)
> for hierarchy-based individual email assignments. In v2.15.0, a user matched
> by the standalone email mapping is rejected when SSO reports
> `email_verified: false`, even if `generic_require_verified_email` / Helm
> `config.genericRequireVerifiedEmail` is disabled.
>
> The standalone `organization_mapping` / `organization_mapping_file` options
> and Helm `config.organizationMapping` / `config.organizationMappingFile` are
> removed in v2.15.1. Move individual emails into the existing
> `organizationHierarchy` members' `userIds`, alongside `ssoGroups`, before
> upgrading. Upgrade the chart and image together and preserve the SQLite
> volume to retain existing account bindings and keys. The implementation
> described below is historical behavior specific to v2.15.0.

- Add email-based organization mapping with inherited memberships by @brtydse100 in [#38](https://github.com/brtydse100/litegate/pull/38)

### Email organization mapping

Deployers can assign emails to groups when SSO group claims are outdated. The
same `levels` array with named `groups` works in inline Helm/Compose values or a
mounted JSON file. Each group's `parent` defines upward inheritance. The original
flat `groups` mapping remains supported; existing SSO group mappings and the
budget-managed organization hierarchy retain their policy precedence.

Startup can provision ordinary LiteLLM users and memberships without generating
keys. Durable bindings in the existing SQLite database connect them to their
authenticated provider identity at first login. Existing unproven email matches
remain pending until SSO confirms ownership; superseded reservations are retained
without deleting users or transferring keys. Membership changes are additive,
so removing configuration does not revoke existing memberships.

### Upgrade

Upgrade the chart and application image together to use the new mapping options.
Preserve the SQLite data volume: identity tables initialize automatically and
existing users and keys require no manual migration. Referenced teams must
already exist. Use one inline or file source and restart after changing a JSON
file; inline Helm changes trigger a rollout. Review pending identities and
retained user records in LiteLLM, including their possible user-count impact.

Every PR now requires a verified preview image from its final commit; official
stable images continue to be published from validated commits on `main`.
