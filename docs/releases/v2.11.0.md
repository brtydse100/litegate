## What's Changed

- Added optional API key storage in the existing SQLite database, disabled by
  default. Owners can show their saved keys again, and administrators can reveal
  stored keys from the installation key list. Reveals verify current ownership
  against LiteLLM, preserve session and CSRF protections, return
  `Cache-Control: no-store`, and audit without credentials.
- Preserved the working replacement during key regeneration when SQLite cleanup
  fails after successful LiteLLM revocation. Cleanup warnings exclude credentials,
  and stale copies of revoked keys cannot be revealed.
- Added manual OIDC endpoint configuration for providers that need explicit
  authorization, token, and JWKS endpoints. All three must be configured together;
  issuer, signature, state, and nonce verification remain in place.
- Added an optional default LiteLLM team for SSO users and optional inheritance
  of the full LiteLLM `proxy_admin` role. Scoped and read-only administrators are
  not promoted, and a default team does not bypass required group mapping.
- Expanded Helm configuration with custom CA bundles and templated additional
  Kubernetes resources, including OpenShift Routes. Restored configuration and
  credential values while preserving the legacy `oidcRequireTeamMapping` and
  `managementApiKey` settings.
- Added a complete Helm environment reference and regression coverage for OIDC,
  authentication compatibility, saved-key access, and failed database cleanup.
  OIDC tests no longer require an undeclared mocking dependency.
- Ordered release publication so the multi-architecture image is published and
  verified with Docker pull/save/load before the GitHub Release is created.
  Official tags must match `VERSION` and point to a commit in `main`; manual
  image tags use `test-` or `dev-`, and shared image aliases are promoted only
  from the current `main` commit.

### Upgrade

No manual database migration is required from 2.10.0. LiteGate creates the new
storage table automatically in the existing SQLite database. Existing Helm
authentication settings remain compatible.

API key storage remains off unless explicitly enabled with
`save_api_keys_in_db: true`, `SAVE_API_KEYS_IN_DB=true`, or Helm
`config.saveApiKeysInDb: true`. Full keys are stored in plaintext, so the database,
its volume, and its backups contain usable credentials. Restrict access to them.
Disabling storage stops saving and revealing keys but retains existing copies.
Keys created before enabling storage, or outside LiteGate, need one regeneration
before they can be shown again. Reveal does not rotate keys or reset spend.

See the [configuration reference](../configuration.md),
[authentication guide](../authentication.md), and
[Helm deployment guide](../../DEPLOYMENT.md) for the new settings.
