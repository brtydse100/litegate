# LiteGate 2.1.0

LiteGate 2.1.0 adds safe, configuration-driven mapping from identity-provider
groups to existing LiteLLM teams.

## Highlights

- Map one SSO group to one or several LiteLLM team IDs.
- Read flat or dotted group claims and match group names case-insensitively.
- Add missing team memberships when a user signs in without removing manually
  managed memberships.
- Optionally reject SSO users who do not match a team mapping.
- Apply the first matched team to newly created and regenerated keys so LiteLLM
  enforces that team's models and budget.
- Show mapped user teams and each key's actual team in the portal.

## Upgrade

Pull the public `ghcr.io/brtydse100/litegate:2.1.0` image, or rebuild from
source. Add a mapping to `config.yaml` only when you are ready:

```yaml
oidc_groups_claim: "groups"
oidc_group_team_mapping:
  Engineering: "team-engineering"
  AI-Platform:
    - "team-platform"
    - "team-shared-services"
oidc_require_team_mapping: false
```

The values are LiteLLM team IDs, not team aliases, and the teams must already
exist. Environment-based deployments use the equivalent one-line JSON value in
`OIDC_GROUP_TEAM_MAPPING`.

## Important behavior

LiteLLM virtual keys accept one team ID. When several mappings match, LiteGate
uses the first team in configuration order as the primary key team while adding
the user to every matched team. Existing keys are unchanged; regenerate them or
update their `team_id` as an administrator.

Membership synchronization is intentionally additive. LiteGate does not remove
memberships automatically because LiteLLM's member-removal operation can also
delete the member's keys for that team.
