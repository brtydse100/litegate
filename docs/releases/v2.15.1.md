## What's Changed

- Fix SSO verification and unify email assignments in organization hierarchy by @brtydse100 in [#40](https://github.com/brtydse100/litegate/pull/40)

### Unified hierarchy assignments

SSO emails now belong in hierarchy members' `userIds`. Email, exact ID, and
SSO group matches resolve one compatible path with existing inherited
memberships and key allowances. Local users keep explicit ID assignments.

### SSO email-verification fix

Fixes v2.15.0's hardcoded rejection of explicitly unverified emails matched by
the standalone email mapping. `generic_require_verified_email` (Helm
`config.genericRequireVerifiedEmail`) now governs generic SSO consistently:
`true` rejects an explicitly false `email_verified` claim, while `false` permits
it. Hierarchy email and SSO-group assignments do not override this choice.
Missing verification claims retain their existing behavior; OIDC token
verification and its existing email behavior are unchanged.

### Upgrade

> [!IMPORTANT]
> This release removes the separate email-mapping configuration introduced in
> v2.15.0. Nonempty old options fail startup with migration guidance; updating
> the image alone is insufficient when those options are configured.

1. Upgrade the Helm chart and application image together.
2. Remove `organization_mapping`, `organization_mapping_file`, their environment
   equivalents `ORGANIZATION_MAPPING` / `ORGANIZATION_MAPPING_FILE`, Helm
   `config.organizationMapping` / `config.organizationMappingFile`, and mounts
   used only for the removed standalone JSON mapping.
3. Put individual emails in the existing
   `organizationHierarchy.levels[].groups[].members[].userIds`. Keep `ssoGroups`
   alongside `userIds` on the same hierarchy member; existing exact user IDs,
   parent inheritance, and budget policies remain supported.

For example, within an existing hierarchy's `members` list:

```yaml
- name: Platform
  userIds: [alice@example.com, employee-123]
  ssoGroups: [platform]
```

New users remain config-only until their first authenticated SSO login
provisions the actual subject without generating a key. No pre-login placeholder
account is created.

Preserve the SQLite volume. Existing 2.15.0 canonical provider/subject bindings
continue to work. Unbound reservations require durable ownership evidence;
pending email candidates require their authenticated existing subject. No new
reservations, user deletions, or key ownership transfers occur. Existing spend,
keys, and memberships are retained; revocation remains an operator decision.
